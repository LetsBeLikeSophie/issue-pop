# news-backend (v0 프로토타입)

RSS 크롤링 + 이슈 클러스터링 + 트렌드 카운트. 오늘 정한 순서대로,
플러터 화면을 만들기 전에 "핵심 로직(클러스터링)이 실제로 되는지"부터
검증하기 위한 최소 버전이에요.

## 구성

- `sources.py` — 수집할 RSS 피드 목록 (매체명, 카테고리, URL, 검증 여부)
- `fetcher.py` — RSS를 받아서 표준 스키마의 기사 리스트로 변환
- `clustering.py` — 기사들을 같은 이슈끼리 묶는 핵심 로직 (TF-IDF + 코사인 유사도 + Union-Find)
- `keyword_extraction.py` — 클러스터에서 짧은 대표 키워드 하나를 뽑는 로직 (예: "국민연금")
- `pipeline.py` — 수집→클러스터링→랭킹 출력까지 이어붙인 실행 파일
- `validate_sources.py` — sources.py의 URL들이 지금 살아있는지 확인하는 스크립트
- `sample_data/sample_articles.json` — 정답을 알고 만든 픽스처(17건, 실제로는 6개 이슈)
- `test_pipeline.py` — 그 정답과 클러스터링 결과가 맞는지 확인하는 회귀 테스트

## 실행 방법

```bash
pip install -r requirements.txt

# 샘플 데이터로 클러스터링 검증 (네트워크 불필요)
python3 pipeline.py

# 테스트
python3 test_pipeline.py

# JSON으로 결과 보기
python3 pipeline.py --json
```

## 중요: 이 세션(샌드박스)에서는 실제 RSS를 못 가져와요

지금 개발 중인 클라우드 환경은 네트워크가 화이트리스트로 제한돼 있어서
`news.google.com` 같은 일반 뉴스 사이트로는 요청이 안 나가요
(`pip install`용 pypi.org 같은 몇몇 도메인만 열려 있음). 그래서:

- `fetcher.py`의 RSS 수집 코드 자체는 정상적으로 짜여 있고, 실제 인터넷이
  되는 곳(로컬 PC, 클라우드 VM 등)에서 `python3 pipeline.py --live`로 돌리면
  진짜 기사를 가져올 거예요.
- 지금 이 세션에서는 대신 `sample_data/sample_articles.json`이라는
  손으로 만든 픽스처로 클러스터링 로직만 검증했어요.

## 검증한 것 / 검증 과정에서 발견한 것

처음에 유사도 임계값을 감으로 0.35로 잡았더니 **아무 기사도 안 묶이는**
문제가 있었어요 (17건이 17개 클러스터로 나옴). 실제 유사도 값을 찍어보니
문자 n-gram 기반 코사인 유사도는 같은 이슈 안에서도 0.1~0.3 정도로 낮게
나오더라고요. 픽스처 데이터로 임계값을 0.06~0.15 범위에서 스캔해서
"진짜 같은 이슈끼리는 묶이고, 다른 이슈끼리는 안 섞이는" 지점을 찾았고
(0.10~0.13 구간), 기본값을 **0.12**로 맞췄어요. 그 결과:

```
1. 국민연금 개편안 관련 — 6건 · 6개 매체
2. 전기요금 인상 관련 — 4건 · 4개 매체
3. 폭염특보 관련 — 3건 · 3개 매체
4. 지하철 파업 관련 — 2건 · 2개 매체
5. 태풍 경로 (단독 보도) — 1건
6. 스타트업 투자 (단독 보도) — 1건
```

이게 정확히 픽스처를 만들 때 의도했던 이슈 구성과 일치해요. 즉
"매체별로 제목이 다 달라도 같은 이슈면 묶인다"는 핵심 아이디어가
최소한 이 정도 규모/난이도에서는 동작한다는 걸 확인한 거예요.

## 업데이트: 키워드 추출 + 매체 목록 확장 (2026-08-23)

`--live`로 실행해보신 뒤 나온 두 가지 질문에 대한 답이에요.

**"키워드가 뭐야?"** — 원래 코드는 클러스터의 대표값으로 `representative_title`
(클러스터 안 기사 한 건의 제목 전체 문장)만 내보내고 있었어요. 와이어프레임의
"오늘 많이 언급된 키워드" 화면이 원하는 건 "국민연금"처럼 짧은 단어였는데
그게 없어서 헷갈리셨을 거예요. `keyword_extraction.py`를 새로 만들어서
클러스터 안 기사들에서 공통으로, 그리고 전체 코퍼스 대비 유독 자주 나오는
단어를 골라내는 로직을 추가했어요 (형태소 분석기 없이 조사만 대충 떼어내는
휴리스틱이라 완벽하진 않지만, 샘플 데이터에서는 "국민연금", "전기요금",
"폭염특보"가 정확히 뽑혀요). 이제 `cluster_articles()` 결과에 `keyword`
필드가 추가로 들어가고, `pipeline.py` 출력도 그걸 앞세우도록 바꿨어요.
기사 1건짜리 단독 이슈는 반복 신호가 없어서 가끔 엉뚱한 단어가 뽑히는
한계가 있어요 (예: "태풍" 대신 "경로") — README 하단에 설명해뒀어요.

**"몇 개 매체야? 다양해야 할 것 같은데"** — 원래 8개였는데 12개를 더
추가해서 20개로 늘렸어요 (조선일보, 중앙일보, 동아일보, MBC, 국민일보,
서울신문, 노컷뉴스, 이데일리, 헤럴드경제, 파이낸셜뉴스, 오마이뉴스, 프레시안).
근데 솔직히 말하면, 저는 이 세션에서 인터넷이 막혀 있어서 이 URL들이
지금도 살아있는지 확인을 못 했어요 — 알려진 패턴으로 추정해서 넣은
거라 `sources.py`에 `"confidence": "unverified"`로 표시해뒀어요. 처음
8개도 "실행하니 되긴 한다"는 말만 들었지 8개 중 몇 개가 실제로 응답했는지는
못 들어서 똑같이 unverified로 뒀고요. 대신 `validate_sources.py`를
만들었으니, 인터넷 되는 PC에서 이거 한 번 돌려서 결과를 알려주시면
살아있는 것만 추려서 확정할게요:

```bash
python3 validate_sources.py
```

## 알려진 한계 (다음에 손볼 곳)

1. **형태소 분석 없음** — 문자 n-gram이라 "국민연금"과 "연금개혁"처럼
   부분적으로만 겹치는 표현엔 약해요. 키워드 추출도 마찬가지로 조사만
   대충 떼어내는 규칙 기반이라 진짜 형태소 분석은 아니에요. 다음 단계는
   `kiwipiepy` 같은 한국어 형태소 분석기로 명사만 뽑아 TF-IDF를 돌리거나,
   더 나아가 `sentence-transformers` 임베딩 기반 유사도로 바꾸는 것.
2. **임계값이 규모에 의존적** — 지금 0.12는 17건짜리 픽스처에 맞춘 값이라,
   실제로 하루 수백~수천 건이 들어오면 다시 튜닝이 필요할 가능성이 높아요.
3. **O(n²) 유사도 행렬** — 기사 수가 많아지면 느려짐. 그때는 LSH나
   벡터 DB(예: FAISS)로 근사 최근접 탐색을 붙이면 돼요.
4. **매체 목록 20개 중 12개가 unverified** — 위 "업데이트" 항목 참고.
   `validate_sources.py` 결과를 주시면 정리할게요.
5. **단독 보도(기사 1건) 클러스터의 키워드 품질** — 반복 신호가 없어서
   가끔 문맥상 덜 중요한 단어가 뽑혀요. 우선순위가 낮은 이유는, 이런
   클러스터는 애초에 랭킹에서 하위권이라 실제 화면에서 눈에 덜 띄기 때문.

## 업데이트: 로컬 PC에서 실제 검증 + 클러스터링 알고리즘 전면 교체 (2026-08-23)

로컬 PC(실제 인터넷 가능)로 옮겨서 `validate_sources.py`와
`pipeline.py --live`를 처음으로 진짜 실행해봤어요. 그 결과 심각한
문제를 발견하고 클러스터링 방식을 통째로 바꿨어요.

**매체 검증 결과**: 20개 중 9개만 생존 (연합뉴스, 한겨레, 경향신문,
매일경제, 머니투데이, SBS, 동아일보, 서울신문, 오마이뉴스). 나머지 11개는
`sources.py`에서 제거했어요 (원본 결과는 `sources_status.json`).

**진짜 RSS로 돌렸더니 threshold=0.12가 완전히 깨졌어요**: 459건 중
368건(80%)이 키워드 "있다"라는 의미 없는 클러스터 하나로 뭉쳐버렸어요.
원인을 파다 보니 예상보다 훨씬 근본적인 문제였어요:

1. **1차 원인 (텍스트 노이즈)**: "(서울=연합뉴스) 김준태 기자 = " 같은
   바이라인, "[포토]" 같은 섹션 태그가 문자 n-gram 유사도를 오염시킴.
   → 정규식으로 제거했지만 효과가 미미했음.
2. **2차 원인 (알고리즘 자체의 결함)**: 진짜 원인은 **Union-Find 기반
   single-linkage 클러스터링**이었어요. 기사쌍 하나만 threshold를 넘어도
   묶어버리는 방식이라, 459개 기사 사이에 평균 연결 차수가 19쯤 되는
   유사도 그래프에서는 (그래프 percolation 이론상) threshold를 얼마로
   잡든 대부분이 사슬처럼 하나로 뭉치는 게 수학적으로 거의 필연이었어요.
   17건짜리 샘플 픽스처는 텍스트가 워낙 적어서 이 문제가 안 드러났을 뿐.

**고친 것**:
- 문자 n-gram → **kiwipiepy 형태소 분석으로 명사만 추출한 뒤, 그 명사
  텍스트에 문자 n-gram TF-IDF** (word-level TF-IDF도 시도했는데, "국민연금"
  vs "연금개혁"처럼 사전 등재 여부에 따라 다른 토큰 취급을 받아서 원래
  같은 이슈가 갈라지는 문제가 있어 폐기).
- Union-Find(single-linkage) → **AgglomerativeClustering(complete-linkage)**.
  클러스터 내 모든 기사쌍이 threshold를 넘어야 합쳐지므로 약한 연결 하나로
  전체가 오염되는 걸 막음.
- 랭킹 정렬을 `article_count` → **`outlet_count` 우선**으로 변경. 한
  매체가 같은 이벤트를 실시간으로 도배하면(예: 머니투데이 야구 경기 사진
  캡션 수십 건) article_count만으로는 "많이 보도된 이슈"처럼 보이지만
  실제론 단독 매체 스트림이라 앱 취지("여러 매체가 보도")와 안 맞음.
- threshold 재튜닝: 0.12 → **0.03** (complete-linkage에서는 같은 threshold
  값이라도 훨씬 엄격하게 작동하기 때문에 값 자체를 다시 스캔해서 잡음).
  `test_pipeline.py` 기준 0.02~0.035 구간에서 안정적으로 정답과 일치함.

**검증 결과**: 459건 → 89개 클러스터, 최대 클러스터가 74건(전체의 16%,
예전엔 80%)까지 줄었고, "폭염주의보"(4매체), "국민연금"(4매체),
"조희대"(6매체) 등 실제로 말이 되는 이슈들이 상위에 옴. 다만 74건짜리
잔여 아티팩트 클러스터(머니투데이+한겨레, 무관한 기사들)가 완전히
사라지진 않았음 — 다만 outlet_count가 2뿐이라 랭킹 우선순위에서 자연스럽게
밀려남. 상세 알고리즘 설명과 한계는 `clustering.py` 상단 docstring 참고.

**아직 남은 것**:
- 위 잔여 아티팩트 클러스터의 근본 원인(한국어 뉴스 텍스트는 일반적인
  어휘만으로도 낮은 코사인 유사도 바닥값이 실제 신호와 겹침)은 완전히
  해결되지 않음. 더 손보려면 sentence-transformers 임베딩 기반 유사도로
  교체하는 게 다음 단계일 것.

## 업데이트: 키워드 추출도 kiwipiepy로 교체 (2026-08-23, 같은 날 두 번째 업데이트)

"이슈판" 뷰어(아티팩트)로 실제 라이브 결과를 훑어보다가 "총리"/"포토"/
"전체" 같은 키워드가 눈에 띄었어요. 원인은 두 가지였고, `keyword_extraction.py`를
`clustering.py`와 같은 전처리를 쓰도록 고쳤어요:

1. **"포토"가 살아남은 이유**: `keyword_extraction.py`가 `clustering.py`의
   바이라인/섹션태그 제거 전처리(`_clean_title`/`_clean_summary`)를 재사용
   안 하고 원본 텍스트를 그대로 토큰화하고 있었음. → 이 전처리를 공용
   모듈 `text_utils.py`로 빼서 두 파일이 같이 씀 (`clustering.py`가
   `keyword_extraction.py`를, `keyword_extraction.py`가 `clustering.py`를
   서로 import하는 순환참조가 생기지 않게 하려고 별도 모듈로 뺐음).
2. **"총리"가 이긴 이유**: 점수 정렬이 "클러스터 내 raw 등장 빈도"를
   1순위로 쓰고 있어서, idf(전역 희소성)는 완전 동점일 때만 보는
   장식이었음. tf\*idf를 1순위로 바꿈. 그 다음 raw tf를 그대로 곱하면
   여전히 등장 횟수가 idf 차이를 압도해서 `log(1+tf)`로 완만하게 눌러서
   곱하도록 조정.

여기에 토큰화 자체도 정규식+조사떼기 휴리스틱에서 kiwipiepy 명사 추출로
바꿨고(clustering.py와 동일), "국민연금"처럼 kiwi가 어절에 따라 한
토큰으로도 두 토큰(국민+연금)으로도 쪼갤 수 있는 문제를 완화하려고
바로 붙어있는 명사쌍을 이어붙인 것도 후보에 추가함(`extract_noun_ngrams`).

**결과**: 샘플 픽스처 기준 "국민연금"→"연금"(이 클러스터가 사실 "국민연금
보험료율" + "연금개혁 공청회" 두 하위주제를 아우르고 있어서 오히려 더
정확한 키워드), "전기요금"→"요금인상"(통계적으로 4% 이내 차이라 사실상
동급)으로 바뀌었고 `test_pipeline.py` 기대값도 그에 맞춰 갱신함(이유는
테스트 파일 주석 참고). 라이브 데이터에서는 "총리"→"한총리", "포토"/
"전체"/"있다" 같은 키워드는 더 이상 안 나옴 — "종부세"/"폭염주의보"/
"K리그"처럼 실제로 말이 되는 구체적 키워드들이 뽑힘.

**시도했다가 버린 것**: "점수가 근소하게 비슷하면(예: 5% 이내) 더 긴
후보를 우선"하는 규칙도 넣어봤는데, 기사 1건짜리 단독 이슈는 반복
신호가 없어서 거의 모든 후보가 우연히 동점이 되고, 그 상태에서 긴 걸
우선하면 "주말한반도"처럼 문장에서 아무 단어나 이어붙인 게 이겨버리는
역효과가 있었음. 그래서 "점수가 완전히 같을 때만(예: 폭염특보=특보처럼
그 클러스터에서 항상 붙어다니는 경우)" 긴 쪽을 우선하는 걸로 좁혔고,
그마저도 기사 2건 이상인 클러스터에만 적용함.

## 업데이트: 카테고리 분류 추가 (2026-08-23, 세 번째 업데이트)

이슈가 90개쯤 나오니 flat한 목록으로는 한눈에 안 들어온다는 피드백을
받았어요. 유사도 기반으로 이슈들을 한 번 더 재클러스터링(계층적으로
상위 그룹 만들기)하는 것도 생각해봤는데, 그러면 "부동산세제"처럼 매번
다른 이름의 예측 안 되는 상위 그룹이 나와서 오히려 헷갈릴 수 있겠다
싶었어요. 대신 `category.py`를 새로 만들어서 사람이 이미 익숙한 뉴스
섹션(정치/경제/사회/국제/스포츠/연예/IT과학/기타)으로 분류하는 규칙
기반 분류기를 추가했어요 — 카테고리별 키워드 사전을 만들어두고, 클러스터
안 기사들의 명사 토큰과 제일 많이 겹치는 카테고리를 고르는 방식(학습
데이터 없이 바로 설명 가능한 게 장점, 사전에 없는 표현은 "기타"로 빠짐).

`cluster_articles()` 결과에 `category` 필드가 추가됐고, "이슈판"
아티팩트에도 카테고리별 색깔 배지 + 필터 칩을 붙여서 전체 90개 대신
카테고리 하나(예: 정치 16개)만 볼 수 있게 했어요.

**검증 결과**: 라이브 461건 기준 90개 클러스터 중 "기타"로 빠진 건
7개뿐(나머지 83개는 8개 카테고리 중 하나로 잘 분류됨). 카테고리 사전은
v0라서 실측하면서 계속 보완이 필요할 것 — 예를 들어 "종부세"가 정치로
분류된 것처럼 경제/정치 경계가 모호한 이슈들은 판단이 갈릴 수 있음.

## 업데이트: 2단계(슈퍼그룹) 재클러스터링 (2026-08-23, 네 번째 업데이트)

카테고리 필터를 붙여도 "그래도 87개는 너무 많다, 더 큰 묶음으로 묶을
수 없냐"는 요청을 받았어요. 원본 기사(461건)를 더 낮은 threshold로
다시 묶는 건 이미 실측으로 버린 방법이라(문자 유사도가 스케일에
취약해서 threshold를 낮추면 percolation이 재발함 — 0.03→0.005로
낮추자 최대 클러스터가 92건→114건으로 커지면서 배드민턴/칼럼/대법관
인선/야구 사진이 뒤섞였음), 대신 **"이미 만들어진 87개 이슈 자체"를
문서 하나씩으로 보고 한 번 더 complete-linkage를 돌리는 방식**을
새로 만들었어요(`meta_cluster.py`). 원본 기사보다 훨씬 적고(87개) 이미
정제된 입력이라 스케일 문제가 훨씬 덜함.

**스팸비율 필터**: 실측해보니 예전부터 알던 "곽빈"(92건, 2개 매체뿐인
잔여 percolation 아티팩트) 클러스터 하나가 재클러스터링에도 노이즈를
퍼뜨려서 스포츠/사회/경제 이슈를 섞어버렸음. `article_count/outlet_count`
비율이 비정상적으로 높은(=소수 매체가 도배한) 클러스터는 재클러스터링
대상에서 빼고 단독 그룹으로 남기는 필터(`SPAM_RATIO_LIMIT=10`)를
추가해서 해결함.

**검증 결과**: threshold=0.06 기준 87개 이슈 → 42개 슈퍼그룹으로 줄었고
(거의 절반), 내용도 대체로 코히런트함 — 예: "이대통령/당협/사법부/
용산공원/오세훈" 7개 이슈가 "정치권 동향"으로 자연스럽게 묶임.
`pipeline.py --group`으로 실행하면 이 슈퍼그룹 단위 결과를 볼 수 있고,
"이슈판" 아티팩트도 슈퍼그룹(펼치면 이슈들) → 이슈(펼치면 매체별
기사) 3단 아코디언 구조로 바꿨어요.

**아직 남은 것**: 슈퍼그룹 라벨은 그룹 내 outlet_count가 제일 높은
이슈의 키워드를 그대로 씀(예: "이대통령") — 사람이 보기엔 "정치권
동향"처럼 더 포괄적인 이름이 좋을 수 있는데, 지금은 그런 요약 라벨을
새로 만드는 로직이 없음. LLM으로 라벨을 생성하거나, 그룹 내 공통
키워드를 뽑는 방식을 다음에 고려할 만함.

## 업데이트: 클러스터링 엔진을 문자 n-gram → 한국어 문장 임베딩으로 교체 (2026-08-24, 다섯 번째 업데이트)

"제목만 보고 묶으면 더 단순해지지 않냐"는 질문에서 시작한 실험 시리즈예요.
결론부터: **제목만 쓰는 건 역효과**였고(텍스트가 짧아지니 매체 간 표현
차이를 못 잡아서 오히려 87개→121개 이상으로 더 잘게 쪼개짐), 대신
**임베딩(의미 벡터) 기반 유사도로 바꾸는 게 진짜 개선**이었어요.

**모델 선택 과정**:
1. 범용 다국어 모델(`paraphrase-multilingual-MiniLM-L12-v2`) — 매체별
   "문체"(머니투데이 스포츠 캡션체, 한겨레 칼럼체)를 지나치게 비슷하다고
   판단해서 완전히 다른 주제를 섞어버림. threshold를 0.9까지 올려도
   해결 안 됨. 폐기.
2. 한국어 STS 전용 모델(`jhgan/ko-sroberta-multitask`) — 훨씬 나음.
   "이소희·백하나, 배드민턴 세계선수권 여자복식 31년 만에 우승"과
   "백하나-이소희, 배드민턴 女복식 세계선수권 31년 만의 金"처럼 겹치는
   글자가 거의 없는 서로 다른 매체 헤드라인도 정확히 같은 이슈로 잡아냄
   (문자 n-gram으로는 놓쳤을 케이스). 이걸로 채택.

**진짜 원인은 데이터 버그였다**: 한국어 모델로도 "한겨레 기사들이 문체가
비슷해서 뭉친다"는 문제가 남아있었는데, 파보니 알고 보니 한겨레 RSS의
`summary` 필드에 실제 요약 대신 **썸네일 이미지용 HTML `<table>` 태그가
그대로** 들어있었어요. 무관한 기사들이 이 HTML 조각(모든 기사에 거의
동일하게 반복됨)이 겹쳐서 하나로 묶이고 있었던 거예요(`text_utils.py`의
`clean_summary`에서 HTML 태그 제거 + 엔티티 디코딩 추가로 해결). 이 버그를
고치니 예전부터 방어 로직(`SPAM_RATIO_LIMIT`)까지 만들어뒀던 "곽빈"류
잔여 아티팩트가 실측상 거의 다 사라짐(245개 이슈 중 스팸비율 필터에
걸리는 게 0개).

**threshold 재튜닝**: 이슈 레벨 0.03(문자 n-gram) → **0.45**(임베딩,
코사인 유사도 스케일 자체가 다름), 슈퍼그룹 레벨 0.06 → **0.30**.
샘플 픽스처(17건)에서 정확히 맞는 값(0.40)과 라이브 460건에서 필요한
값(0.45) 사이에 미묘한 차이가 있었는데(0.40에서는 "박은빈 드라마 종영
+ 살인사건 + 병원 응급실 + 정치"가 뒤섞인 클러스터가 있었음), 이번에도
실데이터 쪽을 우선시하고 픽스처 기대값을 갱신함 — 이제 "국민연금"
6건이 "보험료율 인상"(4)과 "청년층 불신·공청회 세대차"(2)로 갈라지는데,
둘 다 여전히 말이 되는 분리라 문제로 안 봄. `test_pipeline.py` 주석에
자세히 남겨둠.

**최종 결과**: 라이브 460건 → 258개 이슈 → **98개 슈퍼그룹**. 최대
이슈 클러스터가 12건 수준으로(예전엔 20~30대) percolation 계열 문제가
거의 안 보임.

**성능/설치 트레이드오프**:
- 인코딩이 문자 n-gram(1초 미만)보다 훨씬 느림 — 로컬 CPU 기준 460건에
  약 20~80초. 실서비스로 가면 임베딩을 미리 계산해 캐싱하거나 배치/GPU
  처리가 필요할 것.
- Windows에서 `sentence-transformers`(torch 포함) 설치가 "파일 이름이나
  확장명이 너무 깁니다"로 실패하는 경우가 있었음(torch 라이선스 폴더
  경로가 260자 제한을 넘어감). `pip install --target=pylibs`로 훨씬
  짧은 경로에 설치하고, `embedding_utils.py`가 그 경로를 자동으로
  `sys.path`에 추가하도록 해서 우회함.

**아직 남은 것**: 슈퍼그룹 라벨은 여전히 그룹 내 대표 이슈의 키워드를
그대로 씀 — LLM 기반 요약 라벨 생성은 다음 단계로 미룸.

## 업데이트: "이슈판" 아티팩트를 다시 평평한 목록으로 되돌림 (2026-08-24, 여섯 번째 업데이트)

슈퍼그룹(2단계) 아코디언 UI에 대해 "그룹 라벨이 그룹 내용을 대표 못 함"
이라는 피드백을 받았어요 — 예를 들어 1위 라벨이 "제청"인데 그 안에
"쓸모" 같은 안 어울려 보이는 이슈가 딸려 있는 식. 원인은 슈퍼그룹
라벨을 "그룹 내 outlet_count 1등 이슈의 키워드"로 그냥 가져다 쓰는
방식이었어요(`meta_cluster.py`) — 묶인 이슈들을 아우르는 새 단어를
만드는 게 아니었음. 이걸 고치려면 LLM 요약 같은 추가 작업이 필요한데,
사용자는 그보다 **애초에 계층 구조 자체를 원하지 않는다**고 명확히
피드백을 줌 — "그냥 키워드들만 있으면 좋겠다".

그래서 아티팩트를 슈퍼그룹 아코디언(3단) 이전의 **평평한 단일 목록**
구조로 되돌리고, 대신 화면에 다 보여주진 않고 매체 커버리지 상위
**30~50개(기본 40개)만** 표시하도록 함(요청 사항). 카테고리 배지 +
필터 칩은 그대로 유지 — 이건 계층이 아니라 "필터"라서 원래 취지와
안 부딪힘.

**meta_cluster.py는 코드로는 남겨둠**: 삭제하진 않았고, 백엔드에서
`pipeline.py --group`으로 여전히 실행 가능함. 다만 "이슈판" 아티팩트
기본 화면에서는 더 이상 안 씀. 나중에 슈퍼그룹 라벨링을 제대로(LLM
요약 등으로) 만들고 싶어지면 재활용할 수 있음.

## 업데이트: 보조 키워드 추가 + 형태소 사전 버그 수정 (2026-08-24, 일곱 번째 업데이트)

키워드 하나만으론 "무슨 부류의 뉴스인지" 여전히 안 보인다는 피드백을
받았어요(예: "제청", "카카오", "낮최고"만 봐서는 맥락을 모름). 두 가지를
고쳤어요:

**1. 보조 키워드 추가.** `keyword_extraction.py`에 `extract_keywords()`를
새로 만들어서(기존 `extract_keyword()`는 그대로 유지, 내부 로직을
`_score_candidates()`로 공통화) 1등 키워드와 겹치지 않는 2등 키워드까지
같이 뽑음. `cluster_articles()` 결과에 `keywords`(리스트) 필드가
추가됨. 예: "제청" → "법관제청 · 조희대", "카카오" → 그대로 두 번째
키워드가 맥락을 보강("주주환원" 등). 화면에서도 1등 키워드 옆에 2등을
작게 붙여서 보여줌.

**2. 숫자+단위 조합을 키워드 후보에 추가.** "낮최고"처럼 숫자가 빠져서
애매한 키워드 문제 — 원래 명사만 후보로 뽑아서 "38도", "3%" 같은
숫자+단위 조합이 후보에 아예 없었음. kiwipiepy가 숫자를 SN, "도"/"%"
같은 단위를 NNB/SW로 태깅하는 걸 이용해서, 바로 붙어있는 숫자+단위
조합도 후보에 넣도록 `text_utils.py`의 `extract_noun_ngrams()`를
확장함.

**3. (겸사겸사 발견) "마운자로" 형태소 분석 버그.** 실측하다가 "마운자"라는
이상한 키워드를 발견함 — kiwipiepy 사전에 "마운자로"(비만치료제 상표명)가
없어서 "마운자"(명사)+"로"(조사)로 잘못 쪼개짐. `kiwi.add_user_word()`로
사용자 사전에 등록해서 고침. `text_utils.py`에 `_USER_WORDS` 리스트로
빼뒀으니 앞으로 비슷한 경우 발견하는 대로 추가하면 됨(근본적으로
신조어/외래어 사전 문제라 계속 나올 수 있음 — v0 단계라 발견 즉시
대응하는 식으로 감).

## 업데이트: 아티팩트 실사용 피드백 2건 반영 (2026-08-24, 여덟 번째 업데이트)

"이슈판" 아티팩트에 직접 댓글로 받은 피드백 두 개를 처리함(Artifact
댓글 스레드 기능으로 받음):

**1. 카드 클릭 후 배경색이 안 돌아오는 버그.** 터치 기기에서 탭하면
`:hover` 스타일이 "고정"되는 흔한 CSS 버그였음 — 터치는 진짜 마우스
호버가 아닌데 브라우저가 탭을 hover로 흉내내면서, 다른 곳을 탭하기
전까진 안 풀림. `@media (hover: hover) and (pointer: fine)`로 감싸서
진짜 마우스가 있는 기기에서만 hover 스타일이 적용되게 고침(터치 기기는
이 미디어쿼리 자체가 안 걸려서 고정될 것도 없어짐).

**2. 보조 키워드가 오히려 산만하다는 피드백.** "직선 · 당원"처럼 추상
명사 둘만 있으면 뭔 얘긴지 안 잡히고, "구속영장 · 경찰관구속"처럼 뜻이
겹치는 경우도 있었음. 좋았던 조합("법관제청 · 조희대", "김정은 ·
트럼프")과 비교해보니 공통점은 **고유명사(인물/기관)가 하나 섞여
있었다는 것** — 고유명사는 "누구/어디" 얘긴지 바로 알려줘서 정보량이
확실함. `keyword_extraction.py`의 `extract_keywords()`를 고쳐서, 뽑힌
2개 키워드 중 고유명사가 하나도 없으면 상위 후보 안에서 고유명사를
찾아 더 약한(마지막) 키워드를 그걸로 바꿔치기하게 함
(`text_utils.py`에 `extract_proper_nouns()` 추가). 겸사겸사 "cm"처럼
숫자 없이 단위만 혼자 남는 파편, "개막"/"개최" 같은 지나치게 일반적인
이벤트 명사도 STOPWORDS에 추가해서 걸러냄.

## 업데이트: FastAPI 엔드포인트 추가 (2026-08-24, 아홉 번째 업데이트)

`api.py` 새로 만듦. 실행: `uvicorn api:app --reload`.

**아키텍처**: 요청마다 클러스터링을 다시 안 돌림 — 임베딩 계산이 460건
기준 20~80초 걸려서 매 요청마다 하면 느리고 서버도 무거워짐. 대신
서버 시작 시 한 번 파이프라인을 돌려 캐시(딕셔너리)를 채우고,
`REFRESH_INTERVAL_SECONDS`(기본 30분)마다 백그라운드 태스크가 재수집·
재클러스터링해서 캐시를 갱신함. API는 항상 이 캐시만 읽어서 응답하니까
요청 자체는 가벼움. 이 구조 덕분에 서버 스펙 요구사항이 낮아져서
인프라 선택(라즈베리파이든 저가 VPS든)과 무관하게 잘 작동함(자세한
인프라 논의는 이 세션의 메모리 참고).

**엔드포인트**:
- `GET /trending?limit=40&category=정치` — Main.dc.html "오늘 많이
  언급된 키워드" 화면용. outlet_count 우선 정렬, 카테고리 필터 지원.
- `GET /issues/{id}` — IssueDetail.dc.html "매체별 보도 분포 + 전체
  관련기사" 화면용. `id`는 클러스터 안 기사 링크(정렬 후 해시)로 만듦 —
  같은 기사 묶음이면 재수집 후에도 대체로 같은 id가 나옴(완전 보장은
  아니지만 v0로 충분).
- `GET /categories` — 카테고리별 이슈 개수.
- `GET /health` — 캐시 상태(이슈 개수, 마지막 갱신 시각, 마지막 에러).
- `POST /refresh` — 수동 갱신 트리거(30분 기다리기 싫을 때, 개발용).

로컬에서 서버 띄우고 4개 엔드포인트 다 실제로 호출해서 검증함(정상
데이터 반환, 존재하지 않는 id는 404, 카테고리 필터 정상 작동).

**검증하면서 새로 알게 된 것**: 카테고리 분포를 보니 "기타"가 257개
이슈 중 61개(약 24%)로 꽤 높음 — `category.py`의 규칙 기반 사전이
아직 v0라 커버리지가 완벽하진 않다는 걸 다시 확인함(기존에 알던
한계, 개선은 다음 단계로 미룸).

## 업데이트: DB 스키마 설계 + 영속화 (2026-08-24, 열 번째 업데이트)

FastAPI를 이미 만들었는데(`api.py`), 나중에 기능을 더 붙일 때 테이블을
갈아엎지 않으려고 앞으로 필요해질 기능들을 염두에 두고 미리 스키마를
짜고 붙였음. 기능 요구사항 정리 → 스키마 설계, 순서로 진행함(구체적인
제품 기획 내용은 이 저장소 밖에 별도로 정리해둠).

**신규 파일**: `db.py` (SQLModel + SQLite, `news_trend.db`).

**테이블 8개**:
- `issues`, `articles` — 클러스터링 결과를 영속화한 버전. `api.py`의
  인메모리 캐시가 30분마다 갈아엎이는 것과 달리 이건 계속 쌓임 — 그래야
  "지난 이슈 다시 보기" 같은 기능이 가능함. id는 `api.py`의
  `_make_id`(기사 링크 해시)를 그대로 씀.
- `cluster_summaries` — 이슈별 요약 텍스트 캐시. **설계 핵심**: 요청할
  때마다 다시 생성하지 않고 이슈당 딱 한 번만 생성해서 재사용하는
  구조 — 그래야 연산/API 호출 비용이 "일일 신규 이슈 개수" 기준으로
  예측 가능해짐(전형적인 캐싱 패턴). 지금은 실제 생성 로직 연동 전이라
  `POST /issues/{id}/summary`로 수동 입력만 되는 스텁 상태 — 캐싱
  구조(테이블 설계)만 먼저 검증함.
- `devices`, `device_keyword_watches` — 로그인 없이도 특정 키워드
  관련 알림을 보낼 수 있게 하는 테이블. 계정과 별개로 기기 식별자
  (push_token)만 있으면 되게 설계함 — 로그인 없이 필요한 유일한 서버
  저장소.
- `users`, `subscriptions` — 로그인/결제용 자리. **지금은 완전히
  비어있는 게 정상** — 즐겨찾기의 1차 저장소는 클라이언트 로컬로 하기로
  했고, 로그인은 아직 안 붙임. 나중에 계정 붙일 때 테이블 구조를 안
  바꿔도 되게 미리 자리만 잡아둔 것.
- `user_favorites` — 로그인한 유저의 즐겨찾기(팔로우) 테이블. 로그인
  전까진 비어있음.

**알려진 한계**: `user_favorites.issue_id`가 30분마다 다시 도는
클러스터링 결과(`issues.id`)를 참조하는데, 같은 사건이라도 클러스터
경계가 살짝 바뀌면 id가 안 겹칠 수 있어서 "즐겨찾기한 이슈가 다음
갱신 때 사라져 보이는" 문제가 생길 수 있음. 지금은 감안하고 감(사용자
확인) — 나중에 "같은 사건 판정"(기사 겹침 비율로 이전 이슈와 매칭)
로직을 붙이면 해결됨.

**검증**: 로컬에서 서버 띄우고 새로 만든 엔드포인트(`/archive`,
`/devices`, `/watches`, `/favorites`, `/issues/{id}/summary`)를 전부
실제로 호출해서 확인함 — 정상 CRUD, 없는 id/device 참조 시 404,
DB에 issues 239개·articles 459개 실제로 쌓이는 것까지 확인. 테스트
중 한글 payload가 깨지는 것처럼 보인 적이 있었는데, API 버그가 아니라
테스트용 curl 요청 파일을 cp949로 잘못 인코딩해서 만든 실수였음(UTF-8로
다시 만드니 정상) — 이 세션에서 반복적으로 겪은 Windows 터미널
인코딩 이슈의 연장선.

## 업데이트: "기타" 비율 개선 + "문화" 카테고리 추가 (2026-08-24, 열한 번째 업데이트)

`category.py`의 "기타" 비율이 높다는 걸 실측해서 확인하고 고쳤어요.

**1단계 — 키워드 사전 보완**: 캐시된 DB(`news_trend.db`)에 쌓인 "기타"
이슈들을 쭉 훑어보니 사전에 없는 실제 표현들이 여럿 보였음. 예를 들어
"오존주의보"/"기본소득"/"반려동물"/"노동자"·"하청"(노동 이슈)/
"태권도"·"아시안게임"·"패럴림픽"(스포츠) 같은 것들. 그리고 예상 못 한
발견 하나 — 한겨레 RSS(`https://www.hani.co.kr/rss/`)에 한글판뿐 아니라
**The Hankyoreh 영문판 칼럼/사설도 섞여 들어오고 있었음**("[Column] Is
Donald Trump good for the Korean Peninsula?" 같은 기사들). kiwipiepy가
영어 단어도 SL(외국어) 태그로 뽑아내긴 하길래, 국제 카테고리에 영어
키워드(trump/korean/peninsula/kim/washington/beijing/seoul/north/korea/
nuclear/ukraine/troops)도 같이 등록함. 이 1단계만으로 기타 비율이
8.6%까지 내려감(직전 실측 기준 10.6%에서).

**2단계 — "문화" 카테고리 신설**: 1단계 이후 남은 "기타"를 다시 보니
전시/공연/무용/문학/음악제 같은 문화·예술 행사 기사가 꽤 있었음.
정치/경제/사회/국제/스포츠/연예/IT과학 8개 섹션 중 어디에도 안 맞아서
전부 기타로 빠지고 있었던 것 — 억지로 "사회"나 "연예"에 끼워맞추면 그
섹션의 의미가 흐려질 것 같아서, 아예 "문화" 카테고리를 새로 추가함
(배지 색은 `CATEGORY_COLORS`에 세이지/테라코타 액센트와 안 부딪히는
번트 오렌지 톤으로 추가). 결과: 기타 비율이 **4.5%**까지 내려감(라이브
RSS 223건 기준, 사회 31.8%/정치 17.5%/경제 15.2%/국제 12.1%/IT과학
5.8%/문화 4.9%/연예 4.5%/기타 4.5%/스포츠 3.6%).

남은 기타(10건 정도)는 사전 보완으로 해결될 성격이 아니라 —
인사동정("[인사] 스마트투데이"), 만평(본문에 "만평"이라는 단어가 실제로
안 나오는 경우), 바둑 기전 결과, 소수정당 동향, 학술 연구 소개 같은
정말로 뉴스 8~9개 섹션 어디에도 안 들어맞는 것들이었음 — 억지로 더
끼워맞추기보다 여기서 멈추는 게 맞다고 판단.

## 업데이트: 플러터 앱 연동하며 발견한 버그 3건 + 다이제스트 알림 준비 (2026-08-25, 열두 번째 업데이트)

`app/` 폴더에 실제 플러터 앱을 붙이기 시작하면서(design/ 와이어프레임을
코드로 옮기는 단계) 실사용 중 발견한 백엔드 버그들.

**1. HTML 엔티티 안 풀리는 버그**: 기사 제목에 `&#039;`/`&quot;` 같은
게 그대로 노출됨(예: `'APB-R3'`가 아니라 `&#039;APB-R3&#039;`). 원인은
`fetcher.py`가 `entry.title`을 그대로 저장하고, `clean_title()`의
`html.unescape()`는 클러스터링 전처리(임베딩용 텍스트)에만 쓰이고
`representative_title`/`cluster["articles"]`의 원본 제목엔 안 걸렸던
것. `fetcher.py`에서 수집 시점에 바로 `html.unescape()` 하도록 고쳐서
근본 해결(모든 소비처에 전파됨).

**2. 날짜 필터가 아예 없었음**: "이슈가 200개가 넘는 게 너무 많다"는
피드백으로 확인해보니, RSS에서 가져온 기사를 발행일 상관없이 다
클러스터링하고 있었음. `fetcher.py`에 30시간 초과 기사를 거르는 필터를
추가함(`MAX_ARTICLE_AGE`). 근데 여기서 진짜 함정 하나 — "날짜 없으면
제외"로 처음 짰다가 **한겨레 기사가 30건 전부 날아가는** 걸 발견함.
확인해보니 한겨레 RSS(`https://www.hani.co.kr/rss/`)는 `published`/
`updated` 필드가 아예 없음(feedparser 파싱 실패가 아니라 피드 자체에
없는 것). 그래서 "날짜가 있는데 오래된 것만" 거르고, 날짜 자체가 없는
기사는 그냥 포함시키는 걸로 수정함. (결과적으로 이 필터는 전체 이슈
개수를 크게 줄이진 못함 — 대부분 매체 RSS가 애초에 최신 기사만 담고
있어서였음. 그래도 "오늘 이슈"라는 정확성 자체는 이제 보장됨.)

**3. `localhost` 호스트명 해석이 이 Windows 환경에서 요청당 약 2초씩
걸림**: 플러터 앱에서 "검색이 느리다"는 피드백을 받고 원인을 추적하다
발견함 — `curl`/`urllib`로 직접 재보니 `http://localhost:8000`은
매번 ~2000ms, 같은 요청을 `http://127.0.0.1:8000`으로 하면 ~90ms.
서버 코드 문제가 아니라 클라이언트가 "localhost"라는 이름을 해석하는
과정 자체가 이 개발 환경에서 느린 것(원인은 특정 안 함 — Windows
DNS 캐시/IPv6 우선순위 등으로 추정). 플러터 쪽 `ApiClient`의
기본 baseUrl을 `127.0.0.1`로 바꿔서 우회함. 배포 환경(실제 도메인)에서는
해당 없는 문제.

**검색 아키텍처 관련 별도 교훈**: 처음엔 "이슈판" 프로토타입만큼
빠르게 하려고 이슈 전체를 기사 목록까지 포함해서(`/trending?limit=1000`)
미리 다 받아두는 식으로 짰다가 첫 로딩이 느려짐 → 통계/검색용
엔드포인트(`/stats`, `/search`)를 요약(기사 목록 제외)만 내려주게
분리 → 그래도 타이핑마다 서버를 부르면 로컬 필터보다 느릴 수밖에
없다는 걸 깨닫고, 결국 "이슈판"이 원래 했던 방식(가벼운 요약 전체를
한 번만 받아서 클라이언트가 들고 있다가 즉시 거르기)으로 되돌아옴 —
다만 기사 목록은 뺀 채로. 홈 화면 기본 목록(`/trending`, 40건)은
여전히 기사 목록까지 포함해서 받아서, 펼치기는 네트워크 없이 즉시
반응함. 검색 결과를 펼칠 때만 그제서야 `/issues/{id}`로 상세를
받아옴. 각 엔드포인트의 역할:
  - `GET /trending` — 홈 기본 목록용, IssueDetail(기사 포함)
  - `GET /search?q=` — 검색용 인덱스, IssueSummary만(빈 q로 부르면
    전체가 옴, 검색 자체는 클라이언트에서 처리)
  - `GET /stats` — 마스트헤드용 이슈/기사 개수 집계만

**다이제스트 알림 스키마 준비**: "정해진 시간에 오늘의 트렌드 요약을
푸시(배너)로 보내주면 좋겠다"는 요청으로, `devices` 테이블에
`digest_hour`(0~23, KST 기준, null이면 끔) 필드 추가하고
`PUT`/`GET /devices/{id}/digest` 엔드포인트 만듦. 기기당 하루 1회.
**실제 발송(FCM 등 푸시 서비스 연동)은 아직 없음** — "설정 저장"까지만

헛된 기대를 주니까, FCM 연동 후에 붙이기로 함.

**다이제스트 스케줄러(발송 대상 찾기까지)**: FCM 자격증명이 없어서(계정
설정이 필요한 부분이라 이 세션에서 대신 할 수 없음) 실제 발송은 못
붙였지만, "누구한테 언제 보내야 하는지 찾아내는" 스케줄러는 만들고
검증까지 함. `_digest_loop()`가 5분마다 `_digest_check()`를 돌려서
지금 KST 시각과 `digest_hour`가 일치하는 기기를 찾고,
`_send_digest_stub()`(실제 발송 대신 로그만 찍음)를 호출함.
`last_digest_sent_at`으로 같은 시간대 중복 발송을 막음(50분 이내 재발송
안 함) — 테스트 중 SQLite가 datetime의 timezone 정보를 버리고 저장하는
바람에(round-trip하면 naive datetime이 됨) 뺄셈에서 `TypeError` 나는
버그를 발견해서 고침(저장할 때 항상 UTC였다는 걸 알고 있으니 읽어올 때
`tzinfo=UTC`를 다시 붙여줌). 수동 테스트용 `POST /digest/run`도
만들어서 실제 시각이 되길 기다리지 않고 바로 검증 가능. curl로 시나리오
3개(시간 일치/불일치, 중복 방지) 다 확인함. 나중에 FCM 연동할 땐
`_send_digest_stub()` 안쪽만 실제 발송 호출로 바꿔 끼우면 됨.

## 업데이트: 완전히 무관한 기사가 한 클러스터에 섞이는 버그 수정 (2026-08-26, 열네 번째 업데이트)

실사용 피드백: "멋쟁이사자처럼해커톤"(1등 키워드)/"성주재단"(2등

DB에서 찾아보니 진짜 버그였음(5건짜리 클러스터에 "성주재단 해커톤"
2건 + "양자컴퓨터 챌린지" 1건 + "반도체 이글-N 발표" 1건 + "핫칩스
반도체엔지니어" 1건이 섞여 있었음).

**원인**: `clustering.py`는 complete-linkage라 "모든" 기사쌍의 유사도가
threshold(0.45) 이상이어야 묶이는데, 실제로 재보니 완전 무관한 기사끼리도
Korean STS 임베딩(ko-sroberta) 기준 유사도가 0.45를 우연히 넘는 경우가
있었음 — 한국 뉴스 헤드라인 특유의 "기관명+발표/개최" 같은 상투적 문형이
실제 의미 유사도보다 높게 나오는 것으로 보임.

**시도했다가 버린 방법 2가지** (둘 다 실측에서 다른 클러스터를 부쉈음):
1. 클러스터 안에서 더 엄격한 threshold(0.6)로 임베딩 유사도 재클러스터링
   → "장미란씨 실종 사건"(11건, 시간순으로 다른 사실을 보도한 진짜 같은
   사건)까지 조각남. 사건이 전개되며 기사마다 강조점이 달라 유사도 편차가
   자연스럽게 커서, 스칼라 threshold로는 "진짜 같은 이슈의 편차"와
   "우연히 비슷한 문형"을 못 갈랐음.
2. 클러스터의 대표 키워드를 하나도 포함 안 하는 기사는 무조건 제외
   → sample_data 픽스처의 "전기요금 인상"(4건), "폭염특보"(3건)까지
   조각남. 같은 사건을 다루면서도 그 클러스터의 구체적 키워드(예:
   "보험료율")를 문자 그대로는 안 쓰는 기사가 꽤 있었음.

**최종 방법** (`clustering.py`의 `_split_by_keyword_membership`): 실측해보니
"무관한 기사가 섞인" 클러스터는 두 패턴으로 나뉨 —
(A) 중심 주제 + 키워드를 아예 안 포함하는 소수 낙오 기사(1/3 이하)만 뺌,
(B) 1·2등 키워드가 서로 다른 기사 무리를 대표하고 거의 안 겹치면(1건
이하) 아예 두 그룹으로 쪼갬. 걸러지거나 쪼개진 기사들은 자기들끼리
다시 한번 묶어봄(우연히 서로 진짜 같은 주제일 수 있어서 — 실측에서
"핫칩스" 낙오 기사가 서로 재결합하는 걸 확인함).

sample_data 픽스처(`test_pipeline.py`)는 전혀 안 건드리면서(사이즈
`[4,4,3,2,2,1,1]` 그대로 통과) 실데이터에서는 원래 버그(성주재단/
양자컴퓨터, 패키징/핫칩스)를 정확히 고치고, 덤으로 비슷한 패턴의 다른
오염 클러스터도 몇 건 더 잡음(예: 정치 토론 클러스터에 섞인 무관한
유시민 발언 기사, 가정폭력 클러스터에 섞인 다른 사건 기사). 남는 한계:
"진짜 같은 사건인데 키워드를 살짝 다르게 쓴 소수 기사"가 가끔 낙오될 수
있음(관대한 쪽으로 설계함 — 큰 클러스터를 부수는 것보다 기사 1건이
낙오되는 게 덜 해로움).

## 업데이트: 같은 사건이 여러 이슈로 쪼개지는 반대쪽 버그 수정 (2026-08-26, 열다섯 번째 업데이트)

바로 위 업데이트를 반영한 직후 실사용 피드백: 랭킹 1위 "8명"(네팔 홍수
한국인 실종, 정부 대응 위주 보도)과 2위 "남동발전"(같은 사고, 소속 회사
위주 보도)이 사실 같은 뉴스 아니냐는 지적. 확인해보니 진짜 같은 사건인데
매체마다 강조하는 사실(정부 대응 vs 회사 대응)이 달라 개별 기사쌍
유사도가 들쭉날쭉했고, complete-linkage는 "가장 안 닮은 기사쌍"까지
threshold(0.45)를 넘어야 하니 애초에(오늘 앞선 수정과 무관하게, 1차
클러스터링 단계에서부터) 못 합쳐진 거였음 — 방금 고친 것과 정반대 방향
버그(정밀도 문제가 아니라 재현율 문제).

**해결**: `meta_cluster.py`에 `merge_duplicate_clusters()` 추가, `pipeline.py`의
`run()`이 클러스터링 직후 이걸 한 번 더 거치게 함. 이미 만들어진 이슈들을
서로 비교해서 "같은 사건인데 못 합쳐진 것"을 사후에 합침. 조건은
(1) 클러스터 평균 임베딩 유사도 ≥ 0.60이고 (2) 두 클러스터가 고유명사를
실제로 공유할 것 — 둘 다 필요함. 시행착오:

- 유사도만 보면 "스타트업"(투자소식 모음, 원래도 여러 스타트업 기사가
  느슨하게 묶인 클러스터)처럼 업계 용어가 많이 겹치는 클러스터가 무관한
  다른 클러스터까지 끌어당김 → 고유명사 공유 조건을 추가.
- 합칠 그룹을 Union-Find(체이닝)로 고르면 "장미란"(실종 사건)이
  "이준석"(정당 대표 사퇴)까지 딸려오는 percolation이 재발함(예전에
  Union-Find를 버리고 complete-linkage로 간 이유와 정확히 같은 문제,
  이 파일 상단 주석 참고) → complete-linkage 원리로 바꿔서 해결.
- complete-linkage는 안전하지만 너무 엄격해서 "8명"↔"남동발전" 원래
  타겟 케이스조차 다 못 합침 → average-linkage로 바꾸니 그 케이스는
  합치면서(랭킹 1위가 8명+남동발전 통합 36건/8매체로) percolation은
  안 생김(실측 확인).
- "유니콘"/"팩토리"처럼 우연히 여러 클러스터 텍스트에 겹쳐 나오는 범용
  단어가 오탐을 냄 → `_GENERIC_ANCHOR_STOPWORDS`에 발견되는 대로 추가
  (`text_utils.py`의 `_USER_WORDS`와 같은 대응 방식).

sample_data 픽스처는 전혀 안 건드림(아무것도 안 합쳐짐, 회귀 없음).
남는 한계: "네팔 홍수" 같은 대형 사건은 완전히 하나로 안 합쳐지고 2~3개
이슈로 남을 수 있음(complete-linkage 원리를 지키는 한 어쩔 수 없는
정밀도-재현율 트레이드오프). "광주"처럼 지명이 서로 다른 스포츠팀
연고지로 우연히 겹치는 것 같은 드문 오탐도 남아있을 수 있음 — 발견되는
대로 계속 보완하면 됨.

## 업데이트: 병합 후 재검증 + 대형 클러스터 키워드가 좁게 뽑히는 문제 수정 (2026-08-27, 열여섯 번째 업데이트)

바로 위 병합 기능을 실사용하며 두 가지를 더 발견함.

**1) 병합 직후에도 무관한 기사가 섞여 보임**: "홍수고립"+"조현"을 합쳤더니
"조현"(외교부장관 발언)과 무관한 기사가 섞여 보인다는 피드백, "70대"+
"연인"을 합쳤더니 실제로는 완전히 다른 가정폭력 사건 여러 건이 섞여
있다는 피드백. 확인해보니 "70대"/"연인" 케이스는 진짜 버그(전 연인
보복 사건 3건 + 아버지의 아들 폭행·감금 사건 3건 + 완전 무관한 사건
2건이 한 카드에 섞여있었음) — clustering.py의 1차 검증(패턴 A/B, 열네
번째 업데이트)과 똑같은 로직을 병합 직후에도 한 번 더 걸면 됨. 이
판정 로직을 `keyword_extraction.split_articles_by_keywords()`로 뽑아내서
clustering.py/meta_cluster.py가 같이 재사용하게 리팩터링함. 결과:
"연인"(전 연인 보복 사건 3건)과 "70대"(아버지 폭행 사건 3건)로 정확히
갈라지고 무관한 2건은 낙오됨.

**2) 큰 클러스터의 대표 키워드가 사건 전체를 잘 대표 못 함**: "홍수고립"/
"9명"(조현) 같은 케이스는 사실 "무관한 기사가 섞인" 게 아니라(60건
가까이 다 진짜 네팔 홍수 얘기), 사건이 크고 갈래가 많다 보니(정부 발표/
회사 발표/피해자 수 등) 대표 키워드 2개로 절반도 못 잡는 문제였음.
실제로 점수를 재보니 "9명"(클러스터 내 커버리지 33%)이 "네팔"(커버리지
100%)보다 점수가 높았음 — `keyword_extraction.py`의 idf가 "이 코퍼스
전체에서 얼마나 희귀한지"만 보고 "이 클러스터를 얼마나 잘 대표하는지"는

나와서 전역 문서빈도가 높아 idf가 낮게 나옴 — "8명"/"9명"처럼 그
클러스터에만 유독 많이 나오는 좁은 표현이 오히려 idf 덕에 이겨버림.

**해결**: `_score_candidates()` 점수에 클러스터 내 커버리지(coverage/
기사수)를 곱함. 단, 작은 클러스터(15건 미만)에는 이 보정을 끔 —
sample_data 픽스처로 실측해보니, 작은 클러스터에선 오히려 "국민연금"
(3/4건에 등장, 커버리지 높음)이 "보험료율"(2/4건, 커버리지 낮지만 더
구체적인 정책 이슈)을 이겨버려서 "연금"이 "국민연금"을 이기던 예전
버그와 같은 종류의 문제가 재발했음(`_COVERAGE_WEIGHT_MIN_ARTICLES = 15`).
큰 클러스터에서만 필요한 보정이라 작은 클러스터의 이미 검증된 동작은
그대로 둠. 실측 확인: 네팔 홍수 클러스터의 대표 키워드가 "9명"→"홍수"

## 업데이트: 로그인(이메일+비밀번호) 추가 (2026-08-28, 열일곱 번째 업데이트)

계정 기능 시작 — 구글/애플 로그인은 각각 API 크리덴셜 발급이 필요해서
(FCM/LLM 키와 같은 종류, 사용자가 직접 콘솔에서 해야 하는 일) 당장은
이메일+비밀번호 방식만 구현함. `db.py`에 `User`(email/password_hash
추가)와 `UserSession`(무작위 토큰을 DB에 저장해두고 대조하는 v0 방식,
정식 JWT 아님) 모델 추가.

`api.py` 새 엔드포인트:
- `POST /auth/signup` — 이메일/비밀번호로 가입, 토큰 발급(비밀번호는
  bcrypt로 해시)
- `POST /auth/login` — 로그인, 새 토큰 발급
- `POST /auth/logout` — 토큰 삭제
- `GET /auth/me` — `Authorization: Bearer <token>` 헤더로 본인 정보 조회

기존 `POST/GET /favorites`도 이번에 같이 손봄 — 원래 클라이언트가
`user_id`를 직접 body에 넣어서 보내는 방식이라 아무 번호나 넣으면 남의
즐겨찾기를 조작할 수 있는 구멍이었음(유료화 스키마 검증용으로 만든
자리라 당시엔 인증이 없었음). 이제 `Authorization` 토큰에서 유저를
알아내는 걸로 바꿔서 막음.

curl로 회원가입→로그인→내정보조회→즐겨찾기추가/조회, 그리고 토큰 없이
호출 시 401 나는지, 잘못된 비밀번호로 로그인 시도 시 401 나는지까지
직접 확인함. 스키마가 바뀌어서(User 테이블에 컬럼 추가) `news_trend.db`
삭제 후 재생성 필요했음.

**남은 것**: 플러터 앱 쪽 로그인/회원가입 화면은 아직 없음(설정 화면의
"게스트 사용자" 카드가 여전히 "준비 중" 상태) — 화면 보면서 다듬을 게
많아서 다음 세션에서 이어감. 소셜 로그인(구글/애플)은 여전히 사용자가
직접 API 크리덴셜을 받아와야 붙일 수 있음.

## 업데이트: 보안 숙제 — 8000번 포트 차단 + 로그인 rate limiting (2026-09-01)

**8000번 포트 외부 접근 차단**: 인스턴스 iptables에서 8000번 허용 규칙을
삭제(`sudo iptables -D INPUT <룰번호>`), `netfilter-persistent save`로
영속화. 이제 8000번은 직접 접근 시 타임아웃 나고, nginx 경유(443)만
정상 응답 — 실제로 둘 다 확인함. (VCN Security List에 남은 8000번
규칙은 이제 실질적 위험은 없지만 정리하려면 OCI 콘솔에서 따로 지워야
함, 급한 건 아님.)

**로그인/가입 rate limiting**: `slowapi` 추가해서 `/auth/login`은
IP당 10회/분, `/auth/signup`은 5회/분로 제한(초과하면 429). 로컬
테스트로 정확히 11번째 요청부터 429 뜨는 것까지 확인함.

**근데 배포하고 나서 진짜 배포 환경에서 다시 테스트해보니 안 걸렸음** —
원인을 파고들어보니, slowapi 기본 키 함수(`get_remote_address`)가
`request.client.host`를 쓰는데, Cloudflare 뒤에서는 이게 무용지물이었음.
uvicorn이 기본적으로 X-Forwarded-For를 신뢰해서 `request.client.host`를
덮어쓰는데, Cloudflare는 요청마다 다른 엣지 서버 IP를 이 헤더에 채워
넣어서 **같은 사람이 연속으로 보낸 요청도 매번 다른 IP로 보임**
(`journalctl`로 실측 확인 — 연속 12번 요청이 12개의 서로 다른 IP로
찍혔음). 그래서 IP당 카운트가 매번 다른 키로 흩어져서 절대 10회를
못 채웠던 것.

Cloudflare가 실제 방문자 IP를 정확히 넣어주는 `CF-Connecting-IP`
헤더를 대신 읽도록 고침(`api.py`의 `_rate_limit_key`). 8000번 포트를
막아둔 덕분에 Cloudflare를 거치지 않고 이 헤더를 위조해서 우회할
방법이 없어서 신뢰해도 됨(두 조치가 서로를 보완하는 구조가 됨). 재배포
후 다시 테스트해서 정확히 11번째 요청부터 429 뜨는 것까지 라이브
환경에서 확인함.

## 업데이트: 오래된 이슈 DB 정리 (2026-09-05)

디비에 이슈가 계속 누적되는지 실측해봄 — 매 30분 갱신마다 새 이슈가
`persist_issues`로 들어가기만 하고 지우는 로직이 없었음. 라이브 서버
DB를 직접 열어봤더니 실측 약 11,900건까지 쌓여있었음(며칠치). 이대로
가면 DB 파일이 계속 커지고, `/archive` 조회도 점점 느려질 수 있음.

`db.py`에 `prune_old_issues(session, retention_days=3)` 추가 — 마지막
갱신(`last_seen_at`)이 3일 넘은 이슈를 지움. `refresh_cache()`에서 매
갱신 주기마다 자동으로 호출됨. 구현할 때 SQLite의 `IN (...)` 변수 개수
제한에 걸릴까봐(1만 건대 id를 다 나열하면), Python 리스트로 id를 모아서
`.in_()`에 넣는 대신 서브쿼리(`select(Issue.id).where(...)`)를 바로
`.in_()`에 넘기는 방식으로 감 — 로컬(14,858건 삭제)과 라이브 서버
(11,915건 삭제) 둘 다 에러 없이 검증함.

즐겨찾기(`user_favorites`)는 별개 테이블이라 이슈가 지워져도 즐겨찾기
자체는 안 지워짐 — 다만 즐겨찾기가 가리키던 이슈가 지워지면
`/favorites` 조회 시 조용히 건너뜀(기존에 있던 "클러스터 경계가 바뀌어

그대로 보여줌.

새 테이블 `device_stock_watches`(`db.py`, device_id+ticker), 새 캐시
`_stock_news_cache`(티커→뉴스 리스트, `refresh_cache()`에서 등록된
모든 티커 + STARTER_TICKERS를 합쳐서 갱신). 엔드포인트:
`GET /devices/{device_id}/stocks`(목록+뉴스, 자동 시드),

`/trending`과 같은 이유로 뉴스 목록을 리스트 응답에 통째로 포함시킴

플러터 쪽은 홈 화면 상단바에 아이콘 하나 추가해서 진입(저장한 이슈
아이콘과 같은 패턴) — 홈 피드 자체(카테고리 탭/카드 목록)에는 아무것도
안 섞음. 살림/재테크/IT 같은 큐레이션 페이지를 만들었다 뺐던 이전
결정(`home_screen.dart` 주석 참고)과 같은 이유 — 관심종목도 클러스터링된
"이슈"가 아니라 사용자가 고른 개별 뉴스 피드라서, 카테고리 탭이나 홈
피드 중간 배너에 섞으면 같은 문제가 재발함.

**출처 투명성**: "이 영어 뉴스들 믿을만한 출처야?"라는 질문을 받고
실제 피드를 열어보니, 야후 파이낸스가 자체 기사가 아니라 Motley
Fool/Barchart처럼 "주식 픽" 스타일 콘텐츠까지 섞어서 보여주는
애그리게이터라는 게 확인됨. "Yahoo Finance"로 뭉뚱그리지 않고 기사
링크의 도메인에서 실제 매체명을 뽑아 헤드라인마다 표시하도록 고침
(`stocks.py`의 `_source_name`, 목록에 없는 도메인은 도메인 문자열
그대로 정직하게 보여줌).

**티커 칩 클릭 → 스크롤 이동 버그**: 칩 목록에서 티커를 누르면 그
종목 카드로 스크롤 이동하는 기능을 추가했는데, 처음엔 화면 아래쪽

그래서 화면 밖 종목 카드의 `GlobalKey.currentContext`가 null이 되어
`Scrollable.ensureVisible`이 조용히 실패하고 있었음(디버그 프린트로
`ctx=null` 확인해서 원인 특정). 이 화면은 종목이 많아야 수십 개
수준이라 가상화가 필요 없다고 보고, `ListView` 대신 `SingleChildScrollView`
+`Column`으로 바꿔서 모든 카드가 항상 마운트되게 해서 해결함
(`stock_watch_screen.dart`).

있어서, `_extract_image()`가 둘 다 시도해보고 없으면 조용히 None —
`text_utils.clean_summary()`가 나중에 `<img>` 태그를 지우는 건 유사도
계산용 정제라서, 이미지 추출은 그 정제가 일어나기 *전*(fetcher.py,
원본 summary 단계)에서 먼저 함.

새 필드 `image`가 Article 표준 스키마에 추가돼서 `clustering.py`를
거쳐(코드 변경 없이 dict가 그대로 통과함) `api.py`의 `ArticleOut`까지
흘러감. DB에 영속화되는 `Article` 테이블(archive용)은 손 안 댐 —
`/archive`가 애초에 기사 목록(이미지 포함 상세)이 아니라 이슈 요약만
내려주기 때문에 지금 당장은 필요 없음.

프론트(`expandable_issue_card.dart`의 `_ArticleLine`)는 이미지 있는
기사만 왼쪽에 44×44 정사각형 썸네일을 보여주고, 없는 기사는 지금처럼
텍스트만 — 아티팩트로 두 가지 시안(기사마다 작은 썸네일 vs 카드
대표 이미지 하나만 크게)을 먼저 비교해보고 전자로 확정함(구현 부담이
적고, 이미지 없는 매체가 섞여도 자연스러워서).

## 업데이트: 오늘의 단어 알림 + LLM 첫 도입 (2026-09-11)

뉴스에서 회자되는데 뜻은 어려운 한자어를 하나 골라 사전 뜻풀이와 함께
알림으로 보내는 기능("옛날 뉴스 보며 단어 공부하듯" 컨셉). 여러 번
설계를 뒤집으면서 확정한 파이프라인:

1. 오늘 기사 제목을 kiwipiepy로 토큰화해서 일반명사(NNG, 3글자 이상)
   후보를 뽑고, **2개 이상의 서로 다른 이슈에서 재등장**하는 것만 남김
   (재등장 = 그날 화제성이 있다는 신호, 오탈자/희귀 고유명사 배제).
2. 국립국어원 "한국어 학습용 어휘 목록"(2003, `known_words.txt`,
   5,543단어)과 수동 관리하는 `_COMMON_STOPWORDS`에 있으면 제외 — "어려운
   단어"이지 "낯선 단어"가 아니라서, 흔히 쓰는 말은 걸러냄. 이 목록은
   2003년 외국인 학습자 기준이라 반도체/데이터/코스닥 같은 현대 외래어/
   전문용어가 안 걸러지는 빈틈이 있어서, `_USER_WORDS`와 같은 방식으로
   발견하는 대로 `_COMMON_STOPWORDS`에 계속 추가하면 됨.
3. 국립국어원 표준국어대사전 Open API(`dictionary.py`)로 뜻풀이가
   실제로 있는 단어만 최종 후보로 남김(사전에 없으면 애초에 "단어
   공부" 취지에 안 맞음).
4. 이 단계까지는 순수 빈도/규칙 기반인데, "빈도가 곧 어려움은 아니다"
   (예: "정부"는 자주 나오지만 안 어려움)라는 피드백으로 마지막에
   Claude Haiku(`llm.py`)에게 최종 후보 목록(단어+뜻풀이+예문)을 주고
   "학습 가치가 가장 높은 하나"를 고르게 함 — 순수 휴리스틱만으로는
   빈도(화제성)와 난이도를 동시에 만족하는 판정이 어려워서 이 프로젝트
   최초로 LLM을 실사용 파이프라인에 넣은 사례. 비용 절감을 위해 모델은
   의도적으로 Haiku 고정(간단한 선택 작업이라 과한 모델 불필요).

예문은 그날 실제 뉴스 제목을 그대로 씀(직접 생성한 예문이라 사전
API의 예문-저작권 조항과 무관). `Device.word_of_day_enabled`로 트렌드
알림과 별개의 토글로 설정 가능(`PUT /devices/{id}/word-of-day-alert`).

## 업데이트: 클러스터 품질 LLM 검증 (2026-09-11)

클러스터링/키워드/카테고리 결과가 실제로 잘 나오고 있는지 사람이 계속
눈으로 훑어보기 어려워서, LLM에게 하루 한 번 통째로 검토시키는 설계를
도입(`cluster_audit.py`). 핵심 결정 두 가지:

- **실시간 30분 클러스터링과는 완전히 분리.** 감사는 매일 새벽 4시(KST)
  한 번만 배치로 돌리고(`CLUSTER_AUDIT_HOUR_KST`), 라이브 화면에 영향을
  주지 않음 — "검증 자체가 화면에 바로 반영돼야 한다"가 아니라 "확인된
  문제를 규칙 파일에 반영해서 다음번 클러스터링부터 자동으로 나아지게
  한다"는 게 목적이기 때문(누적 로그로만 남기는 건 의미가 없다는 피드백
  — 실제로 화면에 반영되는 건 텍스트나 카테고리 사전 자체를 고쳐야만
  일어남).
- **찾아내는 문제 3종류**만 정해서 물어봄(더 막연하게 물으면 노이즈가
  늘어남): ① `keyword_truncated`(키워드가 실제 표현의 일부만 잘린 것,
  `suggested_fix`에 온전한 형태 포함), ② `article_mismatch`(주제는
  비슷하지만 그 키워드가 다루는 사건 자체는 아닌 기사가 섞인 것),
  ③ `category_mismatch`(카테고리가 명백히 틀린 것, `suggested_fix`에
  더 맞는 카테고리 포함).

인프라 스펙(1 vCPU/1GB) 때문에 겪은 문제 두 가지: (1) 첫 버전은 엔드
포인트가 전체 검증(약 20번의 순차 LLM 배치 호출, 수 분 소요)을 다
기다렸다가 응답했는데 Cloudflare/nginx 프록시가 60초에 끊어버려서
작업이 통째로 유실됨 — `asyncio.create_task`로 즉시 응답하고
`_cluster_audit_running` 플래그 + `/status` 폴링 엔드포인트로 바꿈.
(2) 배치 하나 끝날 때마다 바로 DB에 커밋하게 바꿔서, 중간에 끊겨도
그때까지 찾은 건 남게 함(처음엔 전부 끝난 뒤 한 번에 커밋해서 위
타임아웃 문제와 겹쳤을 때 전부 날아갔었음).

첫 실행(252개 이슈 → 12개 배치)에서 89건 발견(category_mismatch 40,
keyword_truncated 25, article_mismatch 24). 이 중 "김승원" 패턴(아래
항목)은 실제로 원인을 찾아 `keyword_extraction.py`를 고치고 회귀
테스트에 고정함 — 나머지는 `GET /admin/cluster-audit/findings`로
계속 확인하며 순차적으로 트리아지 예정.

## 업데이트: 키워드 점수 버그 — "김승원" vs "김승원신약" (2026-09-11)

위 클러스터 감사로 찾아낸 첫 실제 사례. 2026-09-06에 고친 "김승" 잘림
버그(형태소 분석 사전에 없어서 토큰이 쪼개지던 문제, 위 항목 참고)와는
다른 새 버그 — 이번엔 토큰화가 아니라 **점수 계산**이 원인.

`keyword_extraction.py`의 점수(`log1p(tf) * idf * coverage_ratio`)는
자주 등장하는 고유명사일수록 `idf`(전체 기사 중 등장 비율의 역수)가
낮아져서 점수가 깎이는 구조. "김승원"은 과거 기사에도 994/20,636건
등장해서 idf가 낮은데(순위 12위), `extract_noun_ngrams()`가 인접 명사를
붙여 만든 "김승원신약"(이 정확한 글자 조합은 코퍼스에 단 한 번도 없어서
idf가 극단적으로 높음, 순위 1위)이 그 자리를 차지해버림. 기존 보정
로직("뽑힌 키워드 중 고유명사가 하나도 없으면 마지막 자리에 끼워넣기")은
"김승원"이 "김승원신약"의 부분 문자열이라는 이유로 "이미 반영됐다"고
잘못 판단해서 건너뜀 — 그마저도 마지막 자리만 보는 로직이라 "김승원신약"이
1순위를 차지한 이번 케이스엔 애초에 안 맞았음.

고침: 모든 키워드 자리를 검사해서, 실제 고유명사를 포함하지만 그
자체는 아닌 자리를 찾으면 그 자리에서 바로 깨끗한 고유명사로 치환하는
로직 추가. "식약처장, 김승원 신약 로비 의혹에…" 실제 기사를
`sample_data/sample_articles.json`에 18번째 픽스처로 추가하고
`test_pipeline.py`에 회귀 검증을 넣어서 재발을 잡음.
